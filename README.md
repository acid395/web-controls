# web-controls widget

The web-controls agent as a library. A site adds one script and gets a button in the corner. A visitor can click it and type what they want ("show only the lower basin", "how full is Lake Powell compared to its average?"). The agent then operates the page's own controls or answers from what the page shows.

The model runs on the visitor's machine through WebGPU. There's no server, no API key, and nothing about the page leaves the browser.

This is the same agent as the Chrome extension, not a port of it. The build takes `extension/background.js` byte for byte and runs it inside the page. It replaces the Chrome APIs that file talks through with in-page equivalents. Every fix to the extension's agent reaches the widget on the next build.

## Install

Into any web app, from this repository's `widget-package` branch (it isn't on the npm registry yet):

```sh
npm install github:acid395/web-controls#widget-package
```

That branch holds only the built package. It's generated by `node widget/scripts/pack.js --push`, and each commit names the source commit it was built from.

### In the app's code

```js
import { mount } from "web-controls-widget";

const widget = mount({
  title: "Ask Reservoir Watch",
  suggestions: ["show only the lower basin", "how full is Lake Powell?"],
});

// The app's own buttons can drive the same agent.
document.querySelector("#help").onclick = () => widget.ask("explain this chart");
```

Nothing else to configure. With Vite or webpack 5, the model runtime (`web-llm.js`, about 6 MB) and its worker are copied into the app's build as separate files. They're fetched only when a visitor presses **Load model**, so the app's own bundle grows by about 115 KB gzipped.

**React**

```jsx
import { useEffect } from "react";
import { mount } from "web-controls-widget";

export function App() {
  useEffect(() => {
    const widget = mount({ title: "Ask this dashboard" });
    return () => widget.unmount();
  }, []);
  return <Dashboard />;
}
```

**Vue**

```js
import { onMounted } from "vue";
import { mount } from "web-controls-widget";
onMounted(() => mount({ title: "Ask this dashboard" }));
```

**Next.js, Nuxt, SvelteKit.** Importing it on the server is safe, but `mount()` has to run in the browser: inside `useEffect`, `onMounted`, or a `"use client"` component. Called on the server, it throws and says so.

TypeScript types are included.

### Without a bundler

Copy the files in `dist/` into the site and add one tag. It mounts itself once the page has parsed, and loads `web-llm.js` from beside itself.

```html
<script src="/vendor/web-controls/web-controls-widget.js"
        data-title="Ask Reservoir Watch"
        data-suggestions="show only the lower basin|how full is Lake Powell?"></script>
```

## Options

| Option | Script attribute | Default | |
|---|---|---|---|
| `title` | `data-title` | `"Ask this page"` | Header text and button label |
| `placeholder` | `data-placeholder` | | Input placeholder |
| `suggestions` | `data-suggestions` (`\|`-separated) | `[]` | Example prompts shown before the first ask |
| `position` | `data-position` | `"bottom-right"` | or `"bottom-left"` |
| `theme` | `data-theme` | `"auto"` | `"light"`, `"dark"`, or follow the OS |
| `accent` | `data-accent` | `#1a6fd1` | Any CSS color |
| `model` | `data-model` | Llama 3.2 3B | The model a first-time visitor gets |
| `models` | `data-models` (comma-separated) | 1B, 1.5B, 3B, 8B | What the panel's picker offers |
| `autoLoad` | `data-auto-load` | `false` | Start the download when the panel opens, without the button |
| `useModel` | `data-use-model="false"` | `true` | Never load a model; only the page's own controls and the no-model shortcuts |
| `meaning` | `data-meaning` | `false` | Also load the 1 GB embedder that narrows big pages by meaning; without it, they're narrowed by words |
| `worker` | `data-worker="false"` | `true` | Run the model in a Web Worker so it never blocks your UI |
| `webllmUrl` | `data-webllm` | `web-llm.js` beside the widget | Where to load WebLLM from |
| `hotkey` | `data-hotkey="false"` | `true` | Ctrl/Cmd+Shift+Space toggles the panel |
| | `data-capture-feeds="false"` | on | Record the JSON/CSV your page fetches, so questions can be answered from the data behind a chart |
| | `data-manual` | | Load but don't mount; call `WebControls.mount()` yourself |

## API

`mount(options)` returns the widget. Calling it again returns the same one, because there's one agent per page.

- `ask(text)` opens the panel and runs a request. It resolves with the same card the panel draws.
- `open()`, `close()`, `toggle()`
- `loadModel()` starts the download. Progress shows in the panel.
- `setModel(id)` picks a model, remembered per site.
- `modelStatus()` returns `{ ready, loading, fraction, model, where, error, hasGpu }`.
- `inventory()` returns the page as the agent sees it. It's useful for checking what your markup exposes.
- `unmount()`

## Content-Security-Policy

With no CSP, nothing needs changing. With one, the widget needs:

```
script-src   'self' 'wasm-unsafe-eval';
worker-src   'self' blob:;
connect-src  'self' https://huggingface.co https://*.huggingface.co https://*.hf.co https://raw.githubusercontent.com;
```

The model weights come from Hugging Face. The compiled model libraries come from GitHub. Both are fetched once per site, then served from the browser's cache. Without `blob:` in `worker-src`, the model runs on the main thread, which still works but competes with your UI while it generates.

## How it works

```
your page
├── GENERIC (generic-controls.js)      reads and operates the page's controls
├── background.js, inside a function   the agent: shortcuts, step loop, verification
│     └── chrome = chrome-shim.js      tabs.sendMessage → GENERIC, in this page
│                                      runtime.sendMessage → model-host.js
│                                      storage.local → localStorage
└── model-host.js                      WebLLM in a Web Worker
```

The widget's own UI sits in a closed shadow root. Your CSS can't restyle it. The agent can't see it either: GENERIC walks open shadow roots looking for controls, and a closed one has nothing to walk.

## Widget or extension

| | Extension | Widget |
|---|---|---|
| Who installs it | Each user, once | Each site, once, for all its visitors |
| Where it works | Any site the user enables it on | The sites that installed it |
| Steps that load a new page | The run carries on; the extension outlives the page | The run ends with the page. History is kept, and the panel reopens open on the next page. Client-side routing (`pushState`) is followed. |
| The model download | Once, for every site | Once per site. Browser storage is per-origin, so two sites with the widget each download their own copy. |
| Speed | The side panel hosts the model, because Chrome throttles the hidden offscreen document 79x | The page is visible, so it isn't throttled; the worker keeps it off your main thread |
| Hand-written site manifests | USGS, NOAA, forecastpoints | The same ones, loaded only on those URLs |
| What the user grants | Install, then "Enable on this site" | A click on "Load model" |
| Blocked by | Nothing, for the sites it lists | The site's own CSP, which the site controls |

To compare the two on the same pages, `npm run demo` serves `/try-on-any-site.html`. That page has a bookmarklet that puts the widget onto any site.

## Develop

```sh
node widget/scripts/build.js        # dist/ from the extension's sources
node widget/scripts/pack.js         # widget/package/, what npm installs (--push publishes the branch)
node widget/test/widget-test.js     # the built file, mounted in jsdom
node widget/demo/serve.js           # http://localhost:5180
```

The agent's behaviour is tested by the extension's suite (`node extension/test/run-tests.js`). This suite tests the joins: mounting, the agent not seeing the widget, an ask reaching the page and coming back, the model being asked through the in-page host, history surviving a reload, and the named manifests loading on their sites.
